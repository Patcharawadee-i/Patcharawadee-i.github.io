## TL;DR

ถ้า agent ของคุณรันคำสั่งใน sandbox ที่ตั้งใจไม่ให้มีทางไปถึง service ภายใน skill ที่เป็นชุดคำสั่ง
`curl` จะสตาร์ต workflow ไม่ได้ และการเจาะ sandbox ให้ออกได้ไม่ใช่ทางแก้ที่ถูก ให้วาง MCP server
ภายในตัวเล็ก ๆ คั่นระหว่าง agent กับ workflow engine มี tool ไม่กี่ตัวที่ตั้งชื่อแคบ ๆ ไม่มี tool
แบบ "รันอะไรก็ได้" และเก็บกฎอย่าง "ห้ามรันซ้อนระหว่างที่ยังมีงานค้าง" ไว้ใน server ไม่ใช่ในข้อความ
ของ skill ถ้าจะจำกัดว่าใครเรียก server ตัวนั้นได้ด้วย NetworkPolicy ของ Kubernetes ให้จำว่า policy
เป็นแบบ additive: ต้องเอา pod ออกจากกฎกว้าง **และ** เพิ่มกฎแคบ ทำทั้งสองอย่างหรือไม่ทำเลย

## เป้าหมาย

อยากพิมพ์บอก agent ประโยคเดียวเป็นภาษาไทยธรรมดา — "อ่านเอกสารในโฟลเดอร์" — แล้วให้มันรัน
document pipeline ที่มีอยู่และรายงานกลับมา ตัว pipeline มีอยู่แล้วเป็น workflow สองตัวใน Windmill
คือ `read` กับ `book` สิ่งที่ขาดคือส่วนที่ให้ agent สตาร์ตมันได้

## ขั้นที่ 1: ทดสอบ flow ก่อนจะเอาอะไรไปครอบ

กฎที่ตั้งไว้ก่อนเขียน skill: **skill ที่สร้างบน flow ที่ยังไม่ได้ทดสอบ แค่ย้ายความล้มเหลวไปอยู่ในที่
ที่อ่านยากกว่าเดิม** ถ้า workflow พัง ควรได้เห็นใน workflow engine ไม่ใช่เป็นประโยคคลุมเครือ
จาก agent

จึงรัน flow จริงก่อน กับไฟล์ทดสอบ 8 ไฟล์ (9 หน้า):

| การรัน | ผล |
|---|---|
| `read` 8 ไฟล์ | 42.3 นาที |
| `book` ไฟล์ชุดเดียวกัน | 35.7 นาที |
| `read` ตอนไม่มีไฟล์ใหม่ในโฟลเดอร์ | ไม่ถึงครึ่งวินาที (269, 275, 305 และ 419 ms จากสี่รอบ) ไม่ใช้ GPU |
| สลับโมเดล | เข้า 301 วินาที กลับ 242 วินาที |
| โมเดล OCR | 65–140 วินาทีต่อหน้า |

หมายเหตุเรื่องตัวเลขชุดนี้: ตอนนั้น `read` กับ `book` ยังเป็น prototype และเวลาข้างบนรวมเวลาที่
บวกเพิ่มจาก error ที่ยังไม่ได้แก้ ตอนนี้แก้แล้ว `read` เหลือประมาณ 20–30 นาที

เวลาส่วนใหญ่ของ `read` ไม่ได้หมดไปกับการอ่าน แต่หมดไปกับการสลับโมเดลเข้าออก (ประมาณ 4–5 นาที
ต่อขา) กับโมเดล OCR

มีพฤติกรรมสองอย่างที่ควรยืนยันให้ได้ก่อนที่ agent จะเข้ามาแตะ:

- **ไม่มีของใหม่ ก็ไม่มีอะไรเกิดขึ้น** ถ้าไม่มีไฟล์ใหม่ในโฟลเดอร์ การรันจบในไม่ถึงครึ่งวินาทีและ
  ไม่แตะ GPU เลย agent ที่เรียก `read` บ่อยเกินไปจึงแทบไม่มีต้นทุน
- **อ่านซ้ำเฉพาะไฟล์เดียวได้ด้วย hash ของมัน** และอีก 7 ไฟล์ไม่ถูกแตะ การแก้ไฟล์ที่มีปัญหาไฟล์เดียว
  จึงไม่ต้องเสียอีก 42 นาที

## ขั้นที่ 2: กำแพง

วิธีเขียน skill ที่นึกออกเป็นอย่างแรกคือชุดคำสั่ง: `curl` ไปที่ API ของ workflow engine เพื่อสตาร์ต
flow แล้ว `curl` อีกรอบเพื่อดูสถานะ ซึ่งใช้ไม่ได้ที่นี่ และมันไม่ใช่บั๊ก

Hermes ตั้งให้รันคำสั่ง terminal ทุกคำสั่งใน sandbox pod แยกต่างหากได้ จุดประสงค์ทั้งหมดของ
sandbox นั้นคืออะไรก็ตามที่รันในนั้น — รวมถึงโค้ดที่โมเดลเพิ่งเขียนเมื่อครู่ — ต้องไม่มีทางไปถึง
service ภายใน และ Hermes v0.21.3 ก็ไม่มี tool สำหรับยิง HTTP แบบ generic ของตัวเอง พอเอาสองข้อ
นี้มารวมกัน skill ที่เป็นชุดคำสั่ง `curl` ก็ไม่มีที่ให้รัน: ที่เดียวที่ agent รัน `curl` ได้ คือที่เดียว
ที่ต้องเข้าไม่ถึง workflow engine

### ทางเลือกที่ไม่เอา

- **รันคำสั่งใน pod ของ agent เอง** เท่ากับทิ้ง sandbox ไปเลย
- **เจาะรูจาก sandbox ไปหา workflow engine** โค้ดที่ไม่น่าไว้ใจใน sandbox ก็ใช้รูเดียวกันได้ รูไม่รู้
  ว่าใครเป็นคนขอผ่าน
- **เปิด trigger ของ workflow ให้เข้าถึงได้จาก internet** ไม่

ทั้งสามทาง "แก้" ปัญหาด้วยการรื้อสิ่งที่ทำให้ระบบปลอดภัยมาตั้งแต่ต้น

### ทางที่เลือก: MCP server ภายใน

MCP เป็นจุดต่อขยายจุดเดียวของ Hermes ที่ไม่ผ่าน sandbox: tool ของ MCP ถูกเรียกโดยตัว agent เอง
ไม่ใช่โดยคำสั่งที่ agent สั่งรัน ประตูจึงควรอยู่ตรงนั้น — MCP server ตัวเล็กในคลัสเตอร์ ไม่มี public
route รู้วิธีสตาร์ตเฉพาะ flow ที่กำหนดไว้แล้วว่าให้สตาร์ตได้

## ออกแบบประตู

คาดว่าจะมี skill จากงานด้านอื่นตามมาอีก จึงทำเป็น server กลางตัวเดียว `<mcp-server>` สิ่งที่ใช้ร่วมกัน
คือ container ไม่ใช่คำสั่ง: งานแต่ละด้านมี tool ชื่อแคบ ๆ ของตัวเอง

กฎที่ใช้ออกแบบ:

- **tool สามตัว ตั้งชื่อตามสิ่งที่มันทำ: `read`, `book`, `status`** ไม่มี tool แบบ "รัน flow ไหนก็ได้"
  และไม่มี tool แบบ "เรียก URL ไหนก็ได้"
- **token ของ workflow engine เป็นของ server เท่านั้น** agent ไม่จำเป็นต้องถือ และไม่มีอะไรใน
  sandbox จำเป็นต้องเห็น
- **tool ไม่รับ argument ชื่อ `model`** argument ที่ไม่มีอยู่ ก็เอาไปใช้ผิดทางไม่ได้ ฝั่ง pipeline เอง
  ก็ควรบังคับเรื่องเดียวกันซ้ำอีกชั้น คือปฏิเสธโมเดลที่ไม่ใช่ local เพื่อให้การเลือกโมเดลไม่ขึ้นกับสิ่งที่
  agent ส่งเข้ามา
- **agent ขอได้แค่ชื่อ flow ไม่มากกว่านั้น** ไม่มีสิทธิ์ใช้ GPU เอง งาน GPU เข้าคิวที่ worker ตัวเดียว
- **server ไม่มีเหตุผลต้องคุยกับ Kubernetes API** จึงไม่ต้องมี credential ของ Kubernetes เลย

> ⚠️ **tool แบบ generic ตัวเดียวก็ลบล้างทั้งหมดนี้ได้** ทันทีที่ server มี tool แบบ "รัน flow ไหนก็ได้"
> หรือ "เรียก URL ไหนก็ได้" มันจะเลิกเป็นประตู แล้วกลายเป็นรูบนกำแพงที่มีขั้นตอนเพิ่ม: ทุกอย่างที่
> sandbox สร้างมาเพื่อกันไว้กลับเข้าถึงได้อีกครั้ง แค่ผ่าน tool call
{: .warn}

### กฎที่สำคัญต้องอยู่ใน server ไม่ใช่ใน skill

มีกฎข้อหนึ่งที่วางผิดที่ได้ง่าย: ห้ามสตาร์ตรอบที่สองระหว่างที่ยังมีงานรอคิวหรือกำลังรันอยู่

ที่ที่ชวนให้ใส่คือข้อความใน skill — "เช็คสถานะก่อนสตาร์ต" แต่คำสั่งใน skill เป็นแค่มารยาท และ
agent ข้ามมารยาทได้ การตรวจจึงอยู่ใน server คำขอสตาร์ตที่มาถึงระหว่างที่มีงานรอคิวหรือกำลังรัน
จะไม่สตาร์ตอะไร และได้ job id ของงานเดิมกลับไป รูปแบบของคำตอบนั้น (ชื่อถูกแทนด้วย placeholder):

```json
{"ok": false, "state": "already running", "job_id": "<job-id>", "what": "<flow-path>", "running": <true|false>,
 "note": "a <domain> job is already queued or running; nothing was started. Follow that job with <status-tool>."}
```

agent เข้าใจผิดได้ว่ามีงานรันอยู่หรือเปล่า แต่ server เข้าใจผิดไม่ได้

## NetworkPolicy เป็นแบบ additive

server แบบนี้ควรรับการเรียกจากผู้เรียกรายเดียวเท่านั้น คือ agent ใน Kubernetes เรื่องนี้ทำด้วย
NetworkPolicy และท่าที่นึกออกก่อน — เพิ่ม policy แคบที่บอกว่า "เฉพาะ agent เท่านั้นที่เรียก pod นี้ได้"
— จะไม่เปลี่ยนอะไรเลย ถ้ายังมี policy กว้างแบบ "อนุญาต traffic ใน namespace เดียวกัน" เลือก pod
ตัวนั้นอยู่

NetworkPolicy เป็นแบบ additive สิ่งที่ pod รับได้คือ union ของทุกอย่างที่ policy ใดก็ตามที่เลือกมัน
อนุญาตไว้ policy แคบไม่ได้ทับ policy กว้าง มันแค่เพิ่มเข้าไป

จึงต้องแก้สองจุด และสองจุดนี้ได้ผลเมื่อทำคู่กันเท่านั้น ตัวอย่างนี้เป็นฉบับทั่วไป ทุกชื่อเป็น
placeholder:

```yaml
# กฎกว้าง: อนุญาต traffic ใน namespace เดียวกัน ยกเว้น pod ที่ระบุไว้
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: <wide-policy>, namespace: <namespace>}
spec:
  podSelector:
    matchExpressions:
      - {key: app, operator: NotIn, values: [<protected-app>]}
  policyTypes: [Ingress]
  ingress:
    - from: [{podSelector: {}}]
---
# กฎแคบ: มีผู้เรียกรายเดียวที่เข้าถึง pod ที่ป้องกันไว้ได้
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: <narrow-policy>, namespace: <namespace>}
spec:
  podSelector: {matchLabels: {app: <protected-app>}}
  policyTypes: [Ingress]
  ingress:
    - from: [{podSelector: {matchLabels: {app: <caller-app>}}}]
      ports: [{port: <port>, protocol: TCP}]
```

| สิ่งที่ apply | สิ่งที่ pod ที่ป้องกันไว้รับได้ |
|---|---|
| กฎแคบอย่างเดียว โดยกฎกว้างยังเลือก pod อยู่ | ทุกอย่างที่กฎกว้างอนุญาต — กฎแคบไม่ได้เปลี่ยนอะไร |
| เอาออกจากกฎกว้างอย่างเดียว | ทุกอย่าง — pod ที่ไม่มี policy ไหนเลือกจะเปิดรับทั้งหมด |
| เอาออกจากกฎกว้าง **และ** เพิ่มกฎแคบ | ผู้เรียกรายเดียว บน port เดียว |

> ⚠️ **ทำครึ่งเดียวแย่กว่าไม่ทำเลย** ถ้าเอา pod ออกจากกฎกว้างโดยไม่เพิ่มกฎแคบ จะไม่มี policy ไหน
> เลือกมันเลย ซึ่งใน Kubernetes แปลว่ารับ traffic จากทุกที่ และไม่มีอะไรเตือน ให้ทดสอบจากทั้งสองฝั่ง:
> ผู้เรียกที่ควรผ่าน กับ pod อื่นที่ไม่ควรผ่าน
{: .warn}

## description ของ skill คือ trigger ของมัน

agent เลือก skill ด้วยการจับคู่ข้อความที่พิมพ์สั่งกับ description บรรทัดเดียวของ skill description จึงเป็น
ส่วนหนึ่งของการออกแบบความปลอดภัย ไม่ใช่เอกสารประกอบ

description ที่กว้างอย่าง "Read documents" จะไปตรงกับรายงานประจำปีและสัญญาด้วย ซึ่ง pipeline
ไม่ได้สร้างมาสำหรับของพวกนั้น มันจะแปลงออกมาเป็น row ที่ไม่มีความหมาย และเผาเวลา GPU ไปด้วย
description จึงระบุชนิดเอกสารที่ pipeline รองรับแบบเจาะจง และ skill มีหัวข้อ "When to Use" ที่ไล่ว่า
**ไม่ควร** ใช้กับอะไรบ้าง ถ้า agent ไม่แน่ใจ skill บอกให้ถามก่อน

## รายงาน: ตัวเลขเท่านั้น

สิ่งที่รายงานกลับมามีแค่จำนวนไฟล์ ไม่มีข้อความจากเอกสารเลย:

```
done — 8 files read, 6 booked, 2 need a look
```

บวกบล็อกสำหรับ dev ที่มี job id, เวลาแต่ละขั้น และ error ถ้ามี

เหตุผลคือรายงานไม่ได้หยุดอยู่ที่หน้าจอ มันผ่านสามที่: บทสนทนาของ agent, โมเดล และ trace
ถ้ารายงานคัดข้อความจากเอกสารมาใส่ ข้อความนั้นก็จะไปค้างอยู่ทั้งสามที่

แค่จำนวนไฟล์กับ job id ก็พอแล้วสำหรับเอาไปตรวจกับ workflow engine ว่ารันจริงและได้ผลตามนั้น
และสองอย่างนี้ไม่ได้บอกว่าในเอกสารเขียนอะไรไว้

## ตอนนี้จบตรงไหน

การเดินสายใช้งานได้: Hermes ต่อเข้า server ผ่าน Streamable HTTP ใน 801 ms และเจอ tool 3 ตัว

แล้วโมเดลก็รายงานการรันที่ไม่เคยเกิดขึ้น เรื่องนั้นอยู่ในโพสต์ถัดไป

## สิ่งที่ได้เรียนรู้

| สถานการณ์ | สิ่งที่ผิดพลาด | ควรทำอย่างไร |
|---|---|---|
| เอา skill ไปครอบ flow ที่ยังไม่เคยรันจนจบ | ความล้มเหลวย้ายจาก workflow engine ไปอยู่ในประโยคของ agent ซึ่งอ่านยากกว่า | รัน flow จริงก่อน แล้วจดตัวเลขไว้ |
| skill ที่เป็นชุดคำสั่ง `curl` โดยคำสั่งรันใน sandbox | sandbox คือที่เดียวที่ต้องเข้าไม่ถึง service ภายใน จึงสตาร์ตอะไรไม่ได้ | ใช้จุดต่อขยายที่ agent เรียกเองโดยตรง — ที่นี่คือ MCP |
| "ให้ sandbox เข้าถึง service ตัวนั้นตัวเดียวก็พอ" | โค้ดที่ไม่น่าไว้ใจใน sandbox ใช้ทางเดียวกันได้ | ปิด sandbox ไว้เหมือนเดิม แล้ววาง server ที่มี tool ระบุชื่อคั่นกลาง |
| เพิ่ม tool แบบ "รัน flow ไหนก็ได้" เพื่อประหยัดเวลาทีหลัง | server กลายเป็นรูบนกำแพงที่มีขั้นตอนเพิ่ม | tool ชื่อแคบหนึ่งตัวต่อหนึ่งอย่างที่ agent ทำได้ |
| มี argument `model` บน tool | agent หรือ prompt ที่มันอ่านมา เลือกได้ว่าข้อมูลจะไปที่ไหน | ไม่ใส่ argument นั้น และบังคับซ้ำใน pipeline ด้วย |
| เขียน "ห้ามรันสองรอบซ้อนกัน" ไว้ในข้อความของ skill | คำสั่งใน skill เป็นมารยาทที่ agent ข้ามได้ | บังคับใน server แล้วคืน job id ของงานเดิม |
| เพิ่ม NetworkPolicy แคบไว้ข้าง policy กว้าง | policy เป็นแบบ additive จึงไม่มีอะไรเปลี่ยน | เอา pod ออกจากกฎกว้าง **และ** เพิ่มกฎแคบ |
| เอา pod ออกจากกฎกว้างแล้วหยุดแค่นั้น | pod ที่ไม่มี policy ไหนเลือกจะรับทุกอย่าง | ทำทั้งสองอย่างหรือไม่ทำเลย แล้วทดสอบจากทั้งสองฝั่ง |
| description ของ skill กว้างเกินไป | skill ถูกเรียกกับเอกสารที่ pipeline ไม่ได้สร้างมารองรับ | ระบุชนิดเอกสารแบบเจาะจง และไล่ว่าไม่ควรใช้กับอะไร |
| รายงานที่คัดข้อความจากเอกสารมาใส่ | ข้อความนั้นไปค้างอยู่ในบทสนทนา ใน context ของโมเดล และใน trace | รายงานแค่จำนวนไฟล์กับ job id |
