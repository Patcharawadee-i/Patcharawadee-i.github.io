## TL;DR

ถ้า agent รันคำสั่งใน sandbox ที่ตั้งใจปิดไม่ให้เข้าถึง service ภายใน skill ที่เป็นชุดคำสั่ง `curl`
จะเริ่ม workflow ไม่ได้ และการเปิดช่องให้ sandbox ออกไปได้ก็ไม่ใช่ทางแก้ที่ถูก ทางที่ใช้ได้คือวาง MCP
server ภายในตัวเล็ก ๆ ไว้ระหว่าง agent กับ workflow engine ให้มี tool ไม่กี่ตัวที่แต่ละตัวทำได้อย่างเดียว
ไม่มี tool แบบ "สั่งอะไรก็ได้" และให้ server เป็นคนบังคับกฎอย่าง "ห้ามรันซ้อน" เอง ไม่ฝากไว้กับ
ข้อความใน skill ถ้าจะจำกัดว่าใครเรียก server ตัวนั้นได้ด้วย NetworkPolicy ของ Kubernetes ต้องรู้ว่า
policy เป็นแบบ additive: ต้องเอา pod ออกจากกฎกว้าง **และ** เพิ่มกฎแคบ ทำทั้งสองอย่างหรือไม่ทำเลย

## เป้าหมาย

อยากพิมพ์สั่ง agent เป็นภาษาไทยธรรมดาแค่ประโยคเดียวว่า "อ่านเอกสารในโฟลเดอร์" แล้วให้มันรัน
document pipeline และรายงานผลกลับมา ตัว pipeline มีอยู่แล้ว เป็น workflow สองตัวใน Windmill คือ
`read` กับ `book` ที่ยังขาดคือทางให้ agent สั่งเริ่ม workflow สองตัวนี้ได้

## ขั้นที่ 1: ทดสอบ flow ให้ผ่านก่อนสร้าง skill

กฎที่ตั้งไว้ก่อนเขียน skill คือ **ถ้าสร้าง skill บน flow ที่ยังไม่ได้ทดสอบ เวลาพังจะหาสาเหตุยากกว่าเดิม**
ถ้า workflow พัง ควรเห็นใน workflow engine โดยตรง ไม่ใช่เห็นเป็นคำตอบกำกวมจาก agent

จึงรัน flow จริงก่อน กับไฟล์ทดสอบ 8 ไฟล์ (9 หน้า):

| การรัน | ผล |
|---|---|
| `read` 8 ไฟล์ | 42.3 นาที |
| `book` ไฟล์ชุดเดียวกัน | 35.7 นาที |
| `read` ตอนไม่มีไฟล์ใหม่ในโฟลเดอร์ | ไม่ถึงครึ่งวินาที (269, 275, 305 และ 419 ms จากสี่รอบ) ไม่ใช้ GPU |
| สลับโมเดล | เข้า 301 วินาที กลับ 242 วินาที |
| โมเดล OCR | 65–140 วินาทีต่อหน้า |

หมายเหตุเรื่องตัวเลขชุดนี้: ตอนนั้น `read` กับ `book` ยังเป็น prototype และเวลาข้างบนรวมเวลาที่
เพิ่มขึ้นจาก error ที่ยังไม่ได้แก้ ตอนนี้แก้แล้ว `read` เหลือประมาณ 20–30 นาที

เวลาส่วนใหญ่ของ `read` ไม่ได้ใช้ไปกับการอ่านเอกสาร แต่ใช้ไปกับการสลับโมเดลเข้าและออก (ประมาณ
4–5 นาทีต่อครั้ง) กับโมเดล OCR

มีสองเรื่องที่ต้องยืนยันให้ได้ก่อนจะให้ agent เข้ามาใช้:

- **ถ้าไม่มีไฟล์ใหม่ ก็ไม่มีอะไรทำงาน** การรันจะจบในไม่ถึงครึ่งวินาทีและไม่ใช้ GPU เลย ต่อให้ agent
  เรียก `read` บ่อยเกินไป ก็แทบไม่เสียอะไร
- **สั่งอ่านซ้ำเฉพาะไฟล์เดียวได้ โดยระบุ hash ของไฟล์นั้น** อีก 7 ไฟล์จะไม่ถูกอ่านใหม่ ถ้าไฟล์เดียวมี
  ปัญหา จึงไม่ต้องรออีก 42 นาที

## ขั้นที่ 2: ติด sandbox

วิธีเขียน skill ที่นึกออกก่อนคือเขียนเป็นชุดคำสั่ง: ใช้ `curl` เรียก API ของ workflow engine เพื่อเริ่ม
flow แล้วใช้ `curl` อีกครั้งเพื่อดูสถานะ วิธีนี้ใช้ที่นี่ไม่ได้ และไม่ใช่เพราะมีบั๊ก

Hermes ตั้งค่าให้รันคำสั่ง terminal ทุกคำสั่งใน sandbox pod ที่แยกออกมาได้ sandbox มีไว้เพื่อให้ทุกอย่าง
ที่รันในนั้นเข้าถึง service ภายในไม่ได้ ซึ่งรวมถึงโค้ดที่โมเดลเพิ่งเขียนขึ้นมาด้วย และ Hermes v0.21.3
ก็ไม่มี tool สำหรับเรียก HTTP ทั่วไปเป็นของตัวเอง

สองข้อนี้รวมกันแปลว่า skill ที่เป็นชุดคำสั่ง `curl` ไม่มีที่ให้รัน เพราะที่เดียวที่ agent รัน `curl` ได้
คือ sandbox ซึ่งเป็นที่ที่ต้องเข้าไม่ถึง workflow engine

### ทางเลือกที่ไม่เอา

- **รันคำสั่งใน pod ของ agent เอง** เท่ากับเลิกใช้ sandbox
- **เปิดช่องจาก sandbox ไปหา workflow engine** โค้ดที่ไม่น่าไว้ใจใน sandbox ก็ใช้ช่องเดียวกันได้ เพราะ
  ช่องนั้นแยกไม่ออกว่าใครเป็นคนเรียก
- **เปิด trigger ของ workflow ให้เรียกได้จาก internet** ไม่เอาเด็ดขาด

ทั้งสามทางแก้ปัญหาได้ก็จริง แต่แก้ด้วยการรื้อสิ่งที่ทำให้ระบบปลอดภัยทิ้งไป

### ทางที่เลือก: MCP server ภายใน

MCP เป็นช่องทางเดียวของ Hermes ที่ไม่ผ่าน sandbox เพราะ tool ของ MCP ถูกเรียกโดยตัว agent โดยตรง
ไม่ใช่โดยคำสั่งที่ agent สั่งรัน จึงเลือกทำทางเข้าไว้ตรงนี้ เป็น MCP server ตัวเล็กที่อยู่ในคลัสเตอร์
ไม่มี public route และสั่งเริ่มได้เฉพาะ flow ที่กำหนดไว้ล่วงหน้า

## ออกแบบ server

คาดว่าจะมี skill สำหรับงานด้านอื่นตามมาอีก จึงทำเป็น server กลางตัวเดียว ใช้ชื่อว่า `<mcp-server>`
สิ่งที่ใช้ร่วมกันคือ container เท่านั้น ส่วน tool แยกกันตามงาน งานแต่ละด้านมี tool ของตัวเองที่ทำได้
เฉพาะเรื่องของตัวเอง

หลักที่ใช้ออกแบบ:

- **มี tool สามตัว ตั้งชื่อตามสิ่งที่ทำ: `read`, `book`, `status`** ไม่มี tool แบบ "รัน flow ไหนก็ได้"
  และไม่มี tool แบบ "เรียก URL ไหนก็ได้"
- **token ของ workflow engine อยู่กับ server เท่านั้น** agent ไม่จำเป็นต้องมี และสิ่งที่รันใน sandbox
  ก็ไม่จำเป็นต้องเห็น
- **tool ไม่มี argument ชื่อ `model`** เมื่อไม่มี argument นี้ ก็ไม่มีใครใช้มันในทางที่ผิดได้ ฝั่ง pipeline
  เองก็ควรตรวจซ้ำอีกชั้น คือปฏิเสธโมเดลที่ไม่ใช่ local เพื่อให้การเลือกโมเดลไม่ขึ้นกับสิ่งที่ agent ส่งมา
- **agent ทำได้แค่ขอให้รัน flow ตามชื่อ** ไม่มีสิทธิ์ใช้ GPU เอง งานที่ใช้ GPU ทั้งหมดเข้าคิวที่ worker
  ตัวเดียว
- **server ไม่จำเป็นต้องเรียก Kubernetes API** จึงไม่ต้องมี credential ของ Kubernetes เลย

> ⚠️ **tool แบบสั่งอะไรก็ได้เพียงตัวเดียว ทำให้ทั้งหมดนี้ไม่มีความหมาย** ทันทีที่ server มี tool แบบ
> "รัน flow ไหนก็ได้" หรือ "เรียก URL ไหนก็ได้" สิ่งที่ sandbox กันไว้จะกลับมาเข้าถึงได้ทั้งหมด
> เพียงแค่เปลี่ยนจากการรันคำสั่งมาเป็นการเรียก tool
{: .warn}

### กฎสำคัญต้องให้ server บังคับ ไม่ใช่เขียนไว้ใน skill

มีกฎข้อหนึ่งที่มักถูกวางไว้ผิดที่ คือห้ามเริ่มงานใหม่ระหว่างที่ยังมีงานรอคิวหรือกำลังรันอยู่

ที่ที่คนมักใส่กฎนี้คือข้อความใน skill เช่น "ตรวจสถานะก่อนเริ่มงาน" แต่ข้อความใน skill เป็นเพียง
คำแนะนำ agent จะไม่ทำตามก็ได้ จึงให้ server เป็นคนตรวจเอง ถ้ามีคำขอเริ่มงานเข้ามาระหว่างที่ยังมีงาน
รอคิวหรือกำลังรัน server จะไม่เริ่มงานใหม่ และส่ง job id ของงานเดิมกลับไป คำตอบมีรูปแบบนี้ (ชื่อต่าง ๆ
ใช้ placeholder แทน):

```json
{"ok": false, "state": "already running", "job_id": "<job-id>", "what": "<flow-path>", "running": <true|false>,
 "note": "a <domain> job is already queued or running; nothing was started. Follow that job with <status-tool>."}
```

agent อาจเข้าใจผิดว่าไม่มีงานรันอยู่ แต่ server รู้สถานะจริงเสมอ

## NetworkPolicy เป็นแบบ additive

server แบบนี้ควรให้เรียกได้จากที่เดียว คือ agent ใน Kubernetes ใช้ NetworkPolicy ทำเรื่องนี้ วิธีที่
นึกออกก่อนคือเพิ่ม policy แคบที่บอกว่า "ให้เฉพาะ agent เรียก pod นี้ได้" แต่ถ้ายังมี policy กว้างแบบ
"อนุญาต traffic ภายใน namespace เดียวกัน" ครอบ pod ตัวนั้นอยู่ การเพิ่ม policy แคบจะไม่เปลี่ยนอะไรเลย

เหตุผลคือ NetworkPolicy เป็นแบบ additive สิ่งที่ pod รับได้คือผลรวมของทุกอย่างที่ policy ทุกตัวที่ครอบ
pod นั้นอนุญาตไว้ policy แคบไม่ได้ไปหักล้าง policy กว้าง มันแค่เพิ่มสิ่งที่อนุญาตเข้าไปอีก

จึงต้องแก้สองจุด และต้องทำพร้อมกันถึงจะได้ผล ตัวอย่างข้างล่างเป็นแบบทั่วไป ชื่อทั้งหมดเป็น
placeholder:

```yaml
# กฎกว้าง: อนุญาต traffic ใน namespace เดียวกัน ยกเว้น pod ที่ระบุไว้
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: <wide-policy>, namespace: <namespace>}
spec:
  podSelector:
    matchExpressions:
      - {key: app, operator: NotIn, values: [<protected-app>]}
  policyTypes: [Ingress]
  ingress:
    - from: [{podSelector: {}}]
---
# กฎแคบ: มีผู้เรียกรายเดียวที่เข้าถึง pod ที่ป้องกันไว้ได้
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: <narrow-policy>, namespace: <namespace>}
spec:
  podSelector: {matchLabels: {app: <protected-app>}}
  policyTypes: [Ingress]
  ingress:
    - from: [{podSelector: {matchLabels: {app: <caller-app>}}}]
      ports: [{port: <port>, protocol: TCP}]
```

| สิ่งที่ apply | สิ่งที่ pod ที่ต้องการป้องกันรับได้ |
|---|---|
| เพิ่มกฎแคบอย่างเดียว โดยกฎกว้างยังครอบ pod อยู่ | ทุกอย่างที่กฎกว้างอนุญาต กฎแคบไม่ได้เปลี่ยนอะไร |
| เอา pod ออกจากกฎกว้างอย่างเดียว | ทุกอย่าง เพราะ pod ที่ไม่มี policy ตัวไหนครอบจะรับ traffic ทั้งหมด |
| เอา pod ออกจากกฎกว้าง **และ** เพิ่มกฎแคบ | เฉพาะผู้เรียกที่กำหนด บน port ที่กำหนด |

> ⚠️ **ทำแค่ครึ่งเดียวแย่กว่าไม่ทำเลย** ถ้าเอา pod ออกจากกฎกว้างแต่ไม่เพิ่มกฎแคบ จะไม่มี policy ตัวไหน
> ครอบ pod นั้นเลย ซึ่งใน Kubernetes แปลว่ารับ traffic จากทุกที่ และไม่มีอะไรเตือน ต้องทดสอบจากทั้ง
> สองฝั่ง คือจากผู้เรียกที่ควรเข้าได้ และจาก pod อื่นที่ไม่ควรเข้าได้
{: .warn}

## description ของ skill เป็นตัวกำหนดว่า skill จะถูกเรียกเมื่อไร

agent เลือก skill โดยเทียบข้อความที่พิมพ์สั่งกับ description บรรทัดเดียวของ skill description จึงเป็น
ส่วนหนึ่งของการออกแบบความปลอดภัย ไม่ใช่แค่คำอธิบายประกอบ

ถ้า description กว้างอย่าง "Read documents" skill นี้จะถูกเรียกกับรายงานประจำปีหรือสัญญาด้วย ซึ่ง
pipeline ไม่ได้ทำมาเพื่อเอกสารพวกนั้น ผลที่ได้จะเป็น row ที่ใช้ไม่ได้ และเสียเวลา GPU ไปเปล่า ๆ

description จึงระบุชนิดเอกสารที่ pipeline รองรับให้เจาะจง และใน skill มีหัวข้อ "When to Use" ที่บอกว่า
**ไม่ควร** ใช้กับอะไรบ้าง ถ้า agent ไม่แน่ใจ skill กำหนดให้ถามก่อน

## รายงาน: มีแต่ตัวเลข

สิ่งที่รายงานกลับมามีแค่จำนวนไฟล์ ไม่มีข้อความจากเอกสารเลย:

```
done — 8 files read, 6 booked, 2 need a look
```

และมีส่วนรายละเอียดสำหรับนักพัฒนา ซึ่งมี job id, เวลาที่ใช้ในแต่ละขั้น และ error ถ้ามี

เหตุผลคือรายงานไม่ได้หยุดอยู่ที่หน้าจอ มันผ่านสามที่: บทสนทนาของ agent, โมเดล และ trace
ถ้ารายงานคัดข้อความจากเอกสารมาใส่ ข้อความนั้นก็จะไปค้างอยู่ทั้งสามที่

แค่จำนวนไฟล์กับ job id ก็พอแล้วสำหรับเอาไปตรวจกับ workflow engine ว่ารันจริงและได้ผลตามนั้น
และสองอย่างนี้ไม่ได้บอกว่าในเอกสารเขียนอะไรไว้

## ตอนนี้จบตรงไหน

การเชื่อมต่อใช้งานได้: Hermes ต่อเข้า server ผ่าน Streamable HTTP ใน 801 ms และเจอ tool 3 ตัว

แต่หลังจากนั้นโมเดลรายงานงานที่ไม่เคยเกิดขึ้นจริง เรื่องนั้นอยู่ในโพสต์ถัดไป

| สร้าง skill บน flow ที่ยังไม่เคยรันจนจบ | เวลาพัง จะเห็นเป็นคำตอบกำกวมจาก agent แทนที่จะเห็นใน workflow engine | รัน flow จริงก่อน แล้วจดตัวเลขไว้ |
| skill เป็นชุดคำสั่ง `curl` และคำสั่งรันใน sandbox | sandbox เข้าถึง service ภายในไม่ได้ จึงเริ่มงานอะไรไม่ได้ | ใช้ช่องทางที่ agent เรียกเองโดยตรง ซึ่งที่นี่คือ MCP |
| "เปิดให้ sandbox เข้าถึง service ตัวนั้นตัวเดียวก็พอ" | โค้ดที่ไม่น่าไว้ใจใน sandbox ใช้ช่องเดียวกันได้ | ปิด sandbox ไว้ตามเดิม แล้ววาง server ที่มี tool เฉพาะเรื่องไว้ตรงกลาง |
| เพิ่ม tool แบบ "รัน flow ไหนก็ได้" เพื่อความสะดวกในภายหลัง | สิ่งที่ sandbox กันไว้กลับมาเข้าถึงได้ทั้งหมดผ่าน tool | หนึ่ง tool ต่อหนึ่งอย่างที่ agent ทำได้ |
| tool มี argument `model` | agent หรือ prompt ที่ agent อ่านมา เลือกได้ว่าข้อมูลจะถูกส่งไปที่โมเดลไหน | ไม่ใส่ argument นั้น และให้ pipeline ตรวจซ้ำด้วย |
| เขียน "ห้ามรันซ้อน" ไว้ในข้อความของ skill | ข้อความใน skill เป็นแค่คำแนะนำ agent ไม่ทำตามก็ได้ | ให้ server บังคับเอง แล้วส่ง job id ของงานเดิมกลับไป |
| เพิ่ม NetworkPolicy แคบโดยยังมี policy กว้างอยู่ | policy เป็นแบบ additive จึงไม่มีอะไรเปลี่ยน | เอา pod ออกจากกฎกว้าง **และ** เพิ่มกฎแคบ |
| เอา pod ออกจากกฎกว้างแล้วไม่ทำต่อ | pod ที่ไม่มี policy ตัวไหนครอบจะรับ traffic ทั้งหมด | ทำทั้งสองอย่างหรือไม่ทำเลย แล้วทดสอบจากทั้งสองฝั่ง |
| description ของ skill กว้างเกินไป | skill ถูกเรียกกับเอกสารที่ pipeline ไม่รองรับ | ระบุชนิดเอกสารให้เจาะจง และบอกว่าไม่ควรใช้กับอะไร |
| รายงานที่คัดข้อความจากเอกสารมาใส่ | ข้อความนั้นไปค้างอยู่ในบทสนทนา ใน context ของโมเดล และใน trace | รายงานแค่จำนวนไฟล์กับ job id |

ทุกข้อข้างบนมีหลักเดียวกัน: กฎที่สำคัญต้องอยู่ในที่ที่ agent เลี่ยงไม่ได้ คือใน server ใน network หรือ
ทำให้ argument นั้นไม่มีอยู่เลย ข้อความใน skill ใช้บอก agent ว่าต้องทำอะไร แต่บังคับอะไรไม่ได้
