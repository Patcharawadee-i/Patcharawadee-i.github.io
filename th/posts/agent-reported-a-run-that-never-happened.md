การต่อ agent เข้ากับ MCP server เป็นส่วนที่ง่าย ส่วนที่ยากคือรายงานของมันเชื่อได้แค่ไหน ซึ่งขึ้นกับ
โมเดล โมเดลเล็กเขียนรายงานของงานที่ไม่เคยเกิดขึ้น ส่วนโมเดล 12B ไม่แต่งอะไรเลย แต่ต้องเพิ่ม memory
limit จาก 13 GiB เป็น 14 GiB เพราะ Hermes Agent ไม่ยอมสตาร์ตถ้า context ต่ำกว่า 64K ถ้า Hermes
บอกว่า MCP tool ไม่มีอยู่ ทั้งที่ skill เพิ่งบอกให้โมเดลใช้ ให้ปิด tool search แล้วเรียก tool ด้วยชื่อเต็ม
ที่ลงทะเบียนไว้

## โพสต์ที่แล้วจบตรงไหน

[โพสต์ก่อนหน้า]({{ '/th/posts/agent-skill-narrow-mcp-door/' | relative_url }})สร้างประตูแคบ ๆ
ไว้บานเดียว คือ MCP server ภายในที่มี tool สามตัว `read`, `book` และ `status` Hermes ต่อเข้าไปผ่าน
Streamable HTTP ใน 801 ms และเจอ tool 3 ตัว

ส่วนการเชื่อมต่อจบแค่นั้น โพสต์นี้เล่าปัญหาที่ตามมาหลังจากเชื่อมต่อได้แล้ว

## โมเดลเล็กรายงานงานที่ไม่เคยเกิดขึ้น

การทดสอบแรกใช้โมเดลเล็กที่เป็นค่าเริ่มต้น `gemma4-it:e4b` โดยวางไฟล์ทดสอบจำนวนหนึ่งไว้ในโฟลเดอร์
แล้วสั่งให้อ่านเอกสารในโฟลเดอร์

มันตอบกลับมาเป็นรายงานว่างานเสร็จแล้ว

ที่จับได้คือจำนวนไฟล์ในรายงาน มันมากกว่าจำนวนไฟล์ที่วางไว้ทดสอบไปเยอะ ซึ่งเป็นไปไม่ได้

พอตรวจต่อก็พบว่าหลังรายงานนั้นไม่มีอะไรเลย workflow engine ไม่มีงานนั้น และไม่มีข้อมูลถูกสร้างขึ้นมา
สักชิ้น โมเดลไม่ได้เรียก tool มันเขียนคำตอบของ tool ขึ้นมาเองในข้อความตอบ แล้วบอกว่า "เสร็จแล้ว"
หน้าตาเฉย ทั้งที่ข้างหลังว่างเปล่า

เรื่องนี้เข้าใจได้ คำสั่งและเนื้อหาเป็นภาษาไทย ซึ่งเป็นจุดอ่อนของโมเดลเล็กอยู่แล้ว ตรงกับที่เคยทดสอบ
Gemma 3 ไว้ช่วงกรกฎาคม–สิงหาคม 2025: ตัว 4B ใช้กับภาษาไทยได้ แต่ไม่ดีเท่าตัว 12B และตอนนั้นตัว 12B
ใช้เวลาประมาณสองเท่าของตัว 4B นี่คือ trade-off ระหว่างสองตัวนี้ และสำหรับภาษาไทยก็ยังต้องเลือก 12B
ข้อดีอย่างหนึ่งคือ Gemma 3 12B รันบน Google Colab T4 ได้ จึงทดสอบเองได้โดยไม่ต้องมีเครื่อง

> ⚠️ **รายงานที่โมเดลแต่งขึ้น หน้าตาเหมือนรายงานจริงทุกอย่าง** ครั้งนี้จับได้เพราะจำนวนไฟล์เกินจาก
> ที่มีอยู่จริง ถ้าตัวเลขที่แต่งมาดูสมเหตุสมผล ก็จะไม่มีอะไรสะดุดตาเลย จึงต้องเอา job id ไปตรวจกับ
> workflow engine ทุกครั้ง
{: .warn}

## โมเดล 12B รายงานตรงตามจริง แต่ pod ถูก kill เพราะ memory ไม่พอ

การทดสอบเดียวกันบน `gemma4-it:12b` ให้ผลต่างกัน เมื่อไม่แน่ใจ มันหยุดแล้วถามกลับ และไม่แต่งอะไร
ขึ้นมาเลยในทุกรอบที่ทดสอบ

จากนั้น pod ของโมเดลก็ถูก kill: `OOMKilled`, exit code 137 ที่ memory limit 13Gi

ก่อนถูก kill มีการเก็บค่า memory ทุก 20 วินาที:

| สถานการณ์ | memory ของ container |
|---|---|
| prompt บรรทัดเดียว | 12,001 Mi |
| ตอนโหลด skill แล้ว | 11,993 → 12,301 → 12,965 → 12,916 Mi |

limit อยู่ที่ 13,312 Mi และทุกค่าที่เก็บได้ต่ำกว่านั้น จังหวะที่ memory พุ่งจน pod ถูก kill ตกอยู่ระหว่าง
การเก็บค่าสองครั้ง การเก็บค่าทุก 20 วินาทีบอกได้ว่า pod วิ่งใกล้ limit แต่ไม่ได้บอกจุดสูงสุด

ปัญหา memory spike แบบนี้มีอยู่จริง และไม่ได้เพิ่งมีในโมเดลรุ่นนี้ มันมีมาตั้งแต่ Gemma 3 แล้ว
ตอนทดสอบ Gemma 3 บน Google Colab T4 ก็นั่งเฝ้าดูตอนมันรัน และเห็น memory spike แบบเดียวกัน
T4 ไวต่อ OOM มาก บนนั้นจึงเห็นชัด ส่วนบนเครื่องนี้ pod ตายเพราะเรื่องนี้ไปหนึ่งรอบ

### ลด context ไม่ได้

ทางประหยัด memory ที่นึกออกก่อนคือลด context window แต่ Hermes ไม่ยอม ยังไม่ได้ลองลดจริง
เพราะไปเจอข้อจำกัดนี้ใน source ของ Hermes ใน image v0.21.3 เสียก่อน (ไม่ได้เทียบกับ repository สาธารณะ):

- ค่าคงที่ ใน `agent/model_metadata.py`: `MINIMUM_CONTEXT_LENGTH = 64_000`
- จุดตรวจ ใน `agent/agent_init.py`: `_enforce_minimum_context()` ซึ่ง raise `ValueError`
- ข้อยกเว้นเดียว: provider `lmstudio` ที่ตั้ง `model.context_length` เป็นค่าบวกไว้ชัดเจน

ข้อความที่มัน raise (ตัดท้ายออก):

```
Model {model} has a context window of {ctx:,} tokens, which is below the minimum 64,000 required by Hermes Agent.  Choose a model with at least 64K context.  If your server reports a window smaller than the model's true window, set model.context_length in config.yaml to the real value ...
```

context จึงต้องอยู่ที่ 65,536 เหมือนเดิม สิ่งเดียวที่เปลี่ยนได้คือ limit:

```
-            memory: 13Gi
+            memory: 14Gi
```

หลังจากนั้นเก็บค่า 45 ครั้ง ห่างกันครั้งละ 20 วินาที: นิ่งที่ 11,990 Mi (11.7 GiB) สูงสุด 12,468 Mi
restart 0 ครั้ง วันถัดมาเก็บ 60 ครั้งใน 20 นาที อยู่ระหว่าง 11,190 ถึง 12,096 Mi

### pod ของโมเดลไม่กลับมาเอง

หลังถูก OOM kill pod ของโมเดลควรจะ restart เอง แต่ไม่กลับมา สถานะเป็น
`CreateContainerConfigError` พร้อม event ประมาณนี้ (จากบันทึก ไม่ใช่ข้อความที่ copy มาตรง ๆ):

```
endpoint not found in cache for a registered resource: <npu-resource>
```

pod ขอใช้ NPU ผ่าน device plugin ซึ่งเป็นตัวที่เขียนเองใน
[โพสต์เรื่อง NPU]({{ '/th/posts/fastflowlm-npu-kubernetes/' | relative_url }}) kubelet ไม่มี endpoint
ที่ใช้งานได้ของ resource ตัวนั้นแล้ว จึงส่ง device ให้ container ตัวใหม่ไม่ได้ พอ restart plugin ก็หาย

ปกติ pod ของ DaemonSet ที่พังจะ restart เอง แต่ตัวนี้ทำไม่ได้ และเหตุผลอยู่ในโค้ดของ plugin ที่โพสต์นั้น
เผยแพร่ไว้ มันลงทะเบียนกับ kubelet **ครั้งเดียว** ตอนเริ่มทำงาน แล้วก็รอเฉย ๆ ไม่เคยตรวจว่าทะเบียน
ยังอยู่หรือเปล่า

เรื่องนี้สำคัญเพราะ kubelet ล้าง socket ของ plugin ใน directory device-plugins ทุกครั้งที่มัน restart
และเอกสาร device plugin ของ Kubernetes คาดหวังให้ plugin รู้ตัวเมื่อ kubelet restart แล้วลงทะเบียนใหม่
plugin ที่ไม่ทำแบบนั้นจะตกอยู่ในสภาพนี้:

- process ยังอยู่ และ container ยังเป็น `Running` DaemonSet จึงไม่มีเหตุให้ restart
- kubelet ไม่รู้จัก resource ของมันแล้ว
- pod ที่ถือ device อยู่ก่อนแล้วยังทำงานต่อได้ จึงดูเหมือนไม่มีอะไรผิดปกติ
- pod ตัวแรกที่ต้อง **สตาร์ต** ใหม่จะติด `CreateContainerConfigError`

ยังพิสูจน์ไม่ได้ว่าครั้งนี้เกิดจาก kubelet restart จริง บอกได้แค่ว่าโค้ดเปิดช่องให้เกิดได้ และไม่รู้ว่า
plugin หลุดทะเบียนไปนานแค่ไหน log ของมันก็ตอบไม่ได้ เพราะเขียนแค่บรรทัดเดียวตอนเริ่ม แล้วไม่เขียน
อะไรอีกเลย

OOM ไม่ได้เป็นต้นเหตุของเรื่องนี้ มันแค่ทำให้ปัญหาโผล่ขึ้นมา เพราะเป็นครั้งแรกที่ pod ตัวนั้นต้องสตาร์ตใหม่

> ⚠️ **ถ้า copy device plugin จากโพสต์เรื่อง NPU ไปใช้ โค้ดนั้นมีข้อบกพร่องนี้** มันทำงานได้จนกว่า
> kubelet จะ restart จากนั้นทะเบียนจะหลุดไปเงียบ ๆ ทั้งที่สถานะยังขึ้น `Running` ทางแก้ที่ต้นเหตุคือ
> ลงทะเบียนใหม่เมื่อ kubelet restart: ให้ plugin เฝ้า directory device-plugins แล้วลงทะเบียนอีกครั้ง
> เมื่อ `kubelet.sock` ถูกสร้างขึ้นใหม่ ซึ่งเป็นวิธีที่ plugin ของ upstream ใช้กัน ส่วน liveness probe
> ที่ fail เมื่อไฟล์ socket ของ plugin หายไป เป็นทางอ้อมที่บังคับให้ได้ผลเดียวกัน คือทำให้ container
> ถูก restart แล้วไปลงทะเบียนใหม่ตอนเริ่มทำงาน
{: .warn}

## Hermes บอกว่า tool ไม่มีอยู่

พอโหลด skill แล้ว การรันรอบถัดมาพังแบบใหม่ โมเดลเรียก MCP tool ตัวหนึ่งด้วยชื่อที่ skill บอกไว้
แล้ว Hermes ตอบกลับเป็น error ว่า tool นั้นไม่มีอยู่

ตอนแรกเข้าใจว่าโมเดลโกหกอีกแล้ว แต่ไม่ใช่ error นั้น Hermes เป็นคนตอบเอง และโมเดลรายงานตามจริง

สาเหตุคือฟีเจอร์ของ Hermes ที่ชื่อ tool search เมื่อเปิดอยู่ tool ของ MCP และ plugin จะไม่ถูกวางให้
โมเดลเห็นตรง ๆ แต่ถูกเก็บไว้หลังขั้นตอนค้นหาอีกชั้น Hermes บอกเรื่องนี้ไว้ในบรรทัดตอนสตาร์ต (ตัวเลขสองตัวแทนด้วย placeholder):

```
🔎 Tool Search (tier 1): <number of tools> MCP/plugin tools deferred (~<number of tokens> tokens) behind tool_search/describe/call
```

skill จึงสั่งให้โมเดลใช้ tool ที่โมเดลมองไม่เห็น

แก้สองจุดแล้วหาย จุดแรก ปิด tool search ใน `config.yaml` ของ Hermes:

```yaml
tools:
  tool_search:
    enabled: "off"
```

ต้นทุนคือคำอธิบายของ tool เหล่านั้นจะถูกใส่ไปในทุก prompt แต่ละ prompt จึงใช้ token มากขึ้น
ยังไม่ได้วัดว่าเพิ่มขึ้นเท่าไร

จุดที่สอง skill เรียก tool ด้วยชื่อเต็มที่ลงทะเบียนไว้ Hermes ลงทะเบียน MCP tool ในรูปนี้:

```
mcp__<server>__<tool>
```

ทั้งสองส่วนถูก sanitize และชื่อที่ยาวเกิน 64 ตัวอักษรจะถูกตัดแล้วต่อท้ายด้วย hash
(`mcp_prefixed_tool_name()` ใน `tools/mcp_tool_schema.py`) ชื่อสั้นที่คนเขียน skill นึกถึง จึงไม่ใช่ชื่อ
ที่โมเดลต้องเรียก

## server ปฏิเสธ `book` ทั้งที่ดูเหมือน `read` เสร็จแล้ว

มีครั้งหนึ่งที่ดูเหมือน server ทำงานผิด แต่จริง ๆ แล้ว server ทำถูก

ลำดับเหตุการณ์คือ สั่ง `read` ไป พอเห็นว่าอ่านเอกสารครบแล้ว Hermes ก็ขอ `book` ต่อทันที แต่ server
ตอบว่า "already running" คือยังมีงานรันอยู่ และไม่เริ่มงานใหม่ให้

ตอนนั้นดูเหมือนเป็นบั๊ก เพราะ `read` ดูเหมือนจบไปแล้ว

แต่ `read` ยังไม่จบ หลังอ่านเอกสารเสร็จ flow ยังเหลืออีกขั้นหนึ่ง คือสลับโมเดลหลักกลับเข้ามา ซึ่งใช้เวลา
อีกประมาณ 4 นาที ระหว่างนั้นงานยังนับว่ารันอยู่ การที่ server ปฏิเสธจึงถูกต้อง

ปัญหาจริงคือไม่มีอะไรบอกเรื่องนี้ ไม่มีการแจ้งว่า flow กำลังสลับโมเดลอยู่ มองจากข้างนอกจึงเหมือน
งานจบแล้ว ทั้งที่ยังไม่จบ

Hermes เองก็ไม่ได้แต่งอะไรขึ้นมา มันรายงานตรง ๆ ว่าถูกปฏิเสธ แล้วรอจนงานเดิมจบ

กฎ "ห้ามรันซ้อน" ถูกวางไว้ใน server ตั้งแต่โพสต์ก่อนหน้า และครั้งนี้เห็นผลชัด: server กันไว้ได้ในจังหวะ
ที่ทุกคนที่มองจากข้างนอกเห็นว่างานจบแล้ว

## ผลรอบสุดท้าย

รอบสุดท้ายรันบนโมเดล 12B แล้วเอาตัวเลขในรายงานของ agent ไปเทียบกับที่ workflow engine บันทึกไว้
ผลคือตรงกันทุกตัว เช่น agent รายงานว่างานใช้เวลา 249.3 วินาที ส่วน engine บันทึก `duration_ms`
เป็น 249302 ซึ่งเป็นค่าเดียวกัน และในรายงานไม่มีข้อความจากเอกสารปนมาเลย

ยังมีสองจุดที่ไม่ดี:

- คำสรุปสำหรับคนอ่านสั้นและมีรายละเอียดน้อยกว่าที่ skill กำหนดไว้
- JSON ในส่วนรายละเอียดสำหรับนักพัฒนาใส่เครื่องหมายคำพูดผิดรูปแบบ

ทั้งสองจุดเป็นข้อจำกัดของตัวโมเดล ไม่ได้เกิดจากการเชื่อมต่อระหว่าง agent กับ server

| อาการ | สาเหตุจริง | ทางแก้ |
|---|---|---|
| agent รายงานว่างานเสร็จ โดยจำนวนไฟล์มากกว่าที่มีอยู่จริง และ workflow engine ไม่มีงานนั้นหรือข้อมูลใดเลย | โมเดลเล็กเขียนผลของ tool ขึ้นมาเองแทนที่จะเรียก tool และเนื้อหาภาษาไทยเป็นจุดอ่อนของโมเดลเล็ก | ใช้โมเดล 12B กับงานแบบนี้ และตรวจ job id ทุกตัวกับ engine |
| pod ของโมเดล `OOMKilled` (exit code 137) ทั้งที่ค่าที่เก็บทุก 20 วินาทีไม่เคยถึง limit | จังหวะที่ memory พุ่งตกอยู่ระหว่างการเก็บค่า | ถือว่า "ใกล้ limit" คือเกินแล้ว และเพิ่ม limit (ที่นี่ 13Gi → 14Gi) |
| อยากลด context เพื่อประหยัด memory | Hermes Agent ไม่ยอมสตาร์ตถ้า context ต่ำกว่า 64,000 token | คง context ไว้ แล้วไปเปลี่ยน memory limit |
| pod ติด `CreateContainerConfigError` หลัง restart พร้อม `endpoint not found in cache for a registered resource` ทั้งที่ device plugin ยังขึ้น `Running` | plugin ลงทะเบียนกับ kubelet ครั้งเดียวแล้วไม่ลงอีก พอ kubelet restart มันจึงยังรันอยู่แต่ทะเบียนหลุด | restart plugin เพื่อให้กลับมาใช้ได้ ทางแก้ที่ต้นเหตุคือลงทะเบียนใหม่เมื่อ `kubelet.sock` ถูกสร้างขึ้นใหม่ (liveness probe ที่ไฟล์ socket ของ plugin เป็นทางอ้อมที่บังคับให้ได้ผลเดียวกัน) |
| Hermes บอกว่า MCP tool ไม่มีอยู่ ทั้งที่ skill เพิ่งระบุชื่อ | tool search เก็บ MCP tool ไว้หลังขั้นตอนค้นหา โมเดลจึงมองไม่เห็น | `tools.tool_search.enabled: "off"` และใช้ชื่อเต็ม `mcp__<server>__<tool>` ใน skill |
| server ปฏิเสธ `book` ด้วย "already running" ทั้งที่ `read` ดูเหมือนเสร็จแล้ว | flow ยังสลับโมเดลหลักกลับเข้ามาไม่เสร็จ และไม่มีอะไรแจ้งว่ากำลังสลับอยู่ | การปฏิเสธนั้นถูกต้อง สิ่งที่ขาดคือการแจ้งว่ากำลังสลับโมเดล |
| ตัวเลขตรง แต่สรุปบางและ JSON ใส่เครื่องหมายคำพูดผิด | คุณภาพของโมเดล | ไม่ใช่ปัญหาการเชื่อมต่อ ต้องใช้โมเดลที่ดีขึ้น |

การเชื่อมต่อเป็นส่วนที่ง่าย: ต่อได้ในไม่ถึงวินาที และเจอ tool ครบสามตัว ส่วนรายงานจะเชื่อได้หรือไม่ขึ้นกับโมเดล
ตัวเลขทุกตัวในรายงานจึงต้องตรวจกับ job id ได้ โดยสิ่งอื่นที่ไม่ใช่ agent ตัวที่เขียนรายงานนั้น
