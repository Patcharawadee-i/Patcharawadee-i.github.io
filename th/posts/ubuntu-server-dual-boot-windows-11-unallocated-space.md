## TL;DR

ถ้า shrink พื้นที่ใน Windows ไว้ให้ Ubuntu แล้วตัวติดตั้ง Ubuntu Server มองไม่เห็นพื้นที่นั้น
ให้ทำสองอย่างพร้อมกัน: **สร้างพื้นที่นั้นเป็นไดรฟ์จริงใน Windows (เช่น Drive D:) แทนที่จะปล่อย
เป็น unallocated** และ **ปิด Device Encryption เพื่อให้ไดรฟ์นั้นไม่มี BitLocker** ทำอย่างเดียว
ไม่พอ พอครบทั้งสองอย่างแล้วตัวติดตั้งถึงเลือกไดรฟ์นั้นได้ แล้วค่อยสั่ง format เป็น ext4
ส่วน EFI ให้ใช้ตัวเดิมที่ Windows ใช้อยู่ ห้ามสร้างใหม่

## สเปกเครื่อง

| รายการ | ค่า |
|---|---|
| เครื่อง | MINIX ER937-AI |
| CPU | AMD Ryzen AI 9 HX 370 (12 cores) |
| iGPU | AMD Radeon 890M — `gfx1150` |
| RAM | 32 GB × 2 แถว DDR5-5600 SO-DIMM = 64 GB (รุ่นมาตรฐานให้มา 32 GB ตัวนี้เป็นรุ่นโรงงาน 64 GB) |
| ดิสก์ | NVMe PCIe 4.0 1 TB (ระบบเห็น 953.9 GB) |
| OS ที่ติดมาจากโรงงาน | Windows 11 Pro |
| OS ที่ลงเพิ่ม | Ubuntu Server 26.04.1 LTS (ISO จากหน้าดาวน์โหลดทางการ ไม่ได้อัปเกรดต่อ) |
| Secure Boot | เปิดอยู่ ไม่ได้ปิด |

เครื่องรุ่นนี้มี NPU มาด้วย (สเปกโฆษณารวม CPU+NPU ไว้ที่ 80 TOPS) แต่งานทั้งหมดในบล็อกนี้
ยังไม่ได้แตะ NPU เลย ทุกอย่างวิ่งบน iGPU

ผลลัพธ์สุดท้ายของผังดิสก์:

```
nvme0n1     953.9G
├─nvme0n1p1   100M vfat     /boot/efi     ← ESP ตัวเดิมของ Windows ใช้ร่วมกัน
├─nvme0n1p2    16M                        ← Microsoft Reserved (MSR) ของ Windows
├─nvme0n1p3   128G ntfs                   ← Windows 11
└─nvme0n1p4 825.7G ext4     /             ← Ubuntu Server
```

ไม่มี swap partition — swap 8 GiB ที่ `free` รายงานเป็นไฟล์ที่ตัวติดตั้งสร้างให้เอง
ไม่ได้กินพื้นที่เป็น partition แยก

## จุดเริ่ม: Windows กิน RAM ไป 11-12 GB ตั้งแต่ยังไม่ได้เปิดอะไร

เครื่องนี้ซื้อมาเพื่อทำ AI station โดยเฉพาะ พอ setup Windows 11 ครั้งแรกเสร็จเข้าหน้า desktop
ยังไม่ได้เปิดโปรแกรมอะไรสักตัว RAM ก็ถูกใช้ไป 11-12 GB แล้ว

สำหรับเครื่องใช้งานทั่วไปตัวเลขนี้ไม่ใช่ปัญหา แต่งานที่จะเอาเครื่องนี้ไปทำคือรันโมเดลภาษา
ซึ่ง RAM คือทรัพยากรที่กำหนดว่าจะโหลดโมเดลขนาดไหนได้ การจ่าย 11-12 GB ให้ระบบปฏิบัติการ
ไปเปล่า ๆ จึงไม่คุ้ม

## ทำไมต้อง Server ไม่ใช่ Desktop

ตอนแรกตั้งใจจะลบ Windows ทิ้งไปเลย แต่อาจารย์แนะนำให้ทำ dual boot ไว้ จะได้ยังมีทางถอย
ถ้า Linux มีปัญหา — คำแนะนำนี้ถูก และมันช่วยจริงในเวลาต่อมา

เลือก Ubuntu เพราะเครื่องมือฝั่ง AI ส่วนใหญ่มีคู่มือและ package ที่ทดสอบกับ Ubuntu มากที่สุด
และเลือก **Server ไม่ใช่ Desktop** ด้วยเหตุผลเดียวกับที่ย้ายออกจาก Windows ตั้งแต่แรก:
Server ไม่มี GUI ไม่มี desktop environment ไม่มีบริการพื้นหลังของงานเดสก์ท็อป จึงกิน RAM
น้อยกว่ามาก

วัดจริงหลังใช้งานมาแล้ว 20 ชั่วโมง ไม่มี container รันอยู่:

| ระบบปฏิบัติการ | RAM ที่ใช้ตอน idle |
|---|---|
| Windows 11 (หลังเข้า desktop ครั้งแรก ยังไม่เปิดโปรแกรม) | 11-12 GB |
| Ubuntu Server 26.04.1 LTS (uptime 20 ชม. ไม่มี container) | 1.4 GB |

```
               total        used        free      shared  buff/cache   available
Mem:            60Gi       1.4Gi        43Gi       8.2Mi        16Gi        59Gi
Swap:          8.0Gi       4.0Ki       8.0Gi
```

ต่างกันประมาณ 10 GB ซึ่งบนเครื่องที่จะเอาไปโหลดโมเดล 10 GB ไม่ใช่ตัวเลขเล็ก

## หมายเหตุ: ทำไมใส่ RAM 64 GB แต่ระบบเห็น 60 GB

เรื่องนี้จะกลับมาสำคัญในโพสต์ถัดไปที่ว่าด้วยการรัน vLLM เลยบันทึกไว้ตรงนี้

`dmidecode` ยืนยันว่าเสียบมา 2 แถว แถวละ 32 GB:

```
        Size: 32 GB
        Locator: DIMM 0
        Type: DDR5
        Speed: 5600 MT/s
        Size: 32 GB
        Locator: DIMM 0
        Type: DDR5
        Speed: 5600 MT/s
```

แต่สิ่งที่ kernel รายงาน:

```
MemTotal:       63873580 kB
```

63,873,580 kB = **60.92 GiB** จาก 64 GiB ที่ติดตั้ง หายไป 3.08 GiB

ส่วนที่หายไปไม่ได้เป็นของ iGPU ทั้งหมดอย่างที่หลายคนเข้าใจ (รวมทั้งผมตอนแรก) ตัวที่กินเยอะ
ที่สุดคือ `crashkernel` ที่ถูกตั้งไว้ใน `/proc/cmdline`:

```
crashkernel=2G-4G:320M,4G-32G:512M,32G-64G:1024M,64G-128G:2048M,128G-:4096M
```

อย่าเดาจากตารางนี้ว่าโดนกันไปเท่าไร ให้ถามเคอร์เนลตรง ๆ ว่าจองจริงกี่ไบต์:

```bash
cat /sys/kernel/kexec_crash_size
```

```
1073741824
```

**1 GiB พอดี** ไม่ใช่ 2 GiB ตามช่อง `64G-128G` ที่ตาแรกน่าจะตรงกับเครื่อง 64 GB
เหตุผลคือตอนเคอร์เนลตัดสินใจว่าจะเข้าช่วงไหน มันเห็น RAM ที่ firmware แบ่งไปแล้ว
ซึ่งต่ำกว่า 64 GiB จึงตกไปอยู่ช่วง `32G-64G` ที่ให้ 1024M แทน — ผมเองก็อนุมานผิดในโพสต์
เรื่อง vLLM ตอนแรกก่อนจะมาไล่ตัวเลขจริงตรงนี้

รวมทั้งหมดแล้วได้ภาพนี้:

| ส่วน | ขนาด | ยืนยันจาก |
|---|---|---|
| RAM ที่ติดตั้งจริง | 64 GiB | `dmidecode` เห็น 32 GB × 2 |
| `crashkernel` (kdump) | 1 GiB | `/sys/kernel/kexec_crash_size` |
| VRAM ที่ BIOS แบ่งให้ iGPU | 512 MiB | `rocm-smi --showmeminfo vram` |
| firmware / ACPI / kernel reserved | ~1.6 GiB | ส่วนที่เหลือจากการลบ |
| **เหลือให้ OS ใช้ (`MemTotal`)** | **60.92 GiB** | `/proc/meminfo` |

ประเด็นที่โยงไปโพสต์หน้า: iGPU ตัวนี้ **ไม่มี VRAM เป็นของตัวเอง** มันได้ VRAM จริงมาแค่
512 MiB ที่เหลือต้องยืม RAM ของระบบผ่านกลไกที่เรียกว่า GTT ซึ่งแปลว่าตอนจะโหลดโมเดล
ขนาดหลาย GB ลง GPU เราต้องไปขยาย GTT เอาเอง — เป็นเรื่องของโพสต์ถัดไป

## สิ่งที่ต้องทำใน Windows ก่อนลง Ubuntu

ทำตามลำดับนี้ ข้ามข้อไหนไม่ได้

1. **ปิด Fast Startup**
   Control Panel → Power Options → Choose what the power buttons do →
   Change settings that are currently unavailable → เอาเครื่องหมายถูกออกจาก
   "Turn on fast startup"
2. **ปิด Device Encryption**
   Settings → Privacy & security → Device encryption → ปิด
   (รอจนกระบวนการถอดรหัสเสร็จ ใช้เวลาสักพัก)
   เครื่องนี้เป็น Windows 11 Pro ซึ่งมีหน้า BitLocker เต็มรูปแบบอยู่ที่
   Control Panel → BitLocker Drive Encryption ด้วย แต่ผมใช้ทางลัดที่ Settings
   ตามข้างบนแล้วได้ผล เลยไม่ได้เข้าไปยุ่งกับหน้านั้น
3. **เก็บ BitLocker recovery key ไว้ก่อน** — วิธีอยู่หัวข้อถัดไป
4. **Shrink volume** ใน Disk Management เพื่อแบ่งพื้นที่ให้ Ubuntu
   (เครื่องนี้เหลือ Windows ไว้ 128 GB ที่เหลือยกให้ Ubuntu)
5. **สร้างพื้นที่ที่ shrink มาให้เป็นไดรฟ์จริง** — คลิกขวาที่พื้นที่ unallocated →
   New Simple Volume → ให้เป็น Drive D: **อย่าปล่อยไว้เป็น unallocated เปล่า ๆ**
   เหตุผลอยู่หัวข้อ "ตัวติดตั้งมองไม่เห็นพื้นที่ว่าง"

> ⚠️ **ปิด Fast Startup ก่อนเสมอ** ถ้าไม่ปิด เวลาสั่ง shutdown Windows จะไม่ได้ปิดจริง
> แต่เข้าสู่สถานะกึ่ง hibernate โดย partition ยังถูกล็อกค้างไว้ ถ้า Linux เข้าไปเขียนทับ
> ในสภาพนั้น filesystem ของ Windows พังได้
{: .warn}

## recovery key คืออะไร ทำไมต้องเก็บก่อน

BitLocker เข้ารหัสข้อมูลในดิสก์ไว้ และจะปลดล็อกให้อัตโนมัติตราบใดที่สภาพแวดล้อมตอนบูต
ยังเหมือนเดิม พอมันเจอความเปลี่ยนแปลงที่ไม่คาดคิด มันจะไม่ปลดล็อกให้ แต่จะขึ้นหน้าจอฟ้า
ขอ recovery key 48 หลักแทน

สิ่งที่ทำให้มันขอ key ได้แก่ การแก้ค่าใน BIOS การเปลี่ยน bootloader และการอัปเดต firmware

การทำ dual boot ชนครบทุกข้อ

ถ้าตอนนั้นไม่มี key อยู่ในมือ = เข้า Windows ไม่ได้อีกเลย และข้อมูลข้างในหายถาวร ไม่มีวิธี
กู้อื่น เพราะนั่นคือหน้าที่ของการเข้ารหัสตั้งแต่แรก

ดึง key ออกมาเก็บด้วยการเปิด Command Prompt แบบ Run as administrator แล้วสั่ง

```
manage-bde -protectors -get C:
```

มองหาบรรทัด `Numerical Password` ตัวเลข 48 หลักใต้บรรทัดนั้นคือ recovery key
เก็บไว้นอกเครื่อง — ถ่ายรูป จดใส่กระดาษ หรือเซฟไว้ในมือถือ อย่าเก็บไว้ในเครื่องที่กำลัง
จะแก้ partition อยู่

เครื่องนี้สุดท้ายไม่โดนถาม key เลยตลอดกระบวนการ แต่นั่นเป็นเรื่องของโชค ไม่ใช่เหตุผล
ที่จะข้ามขั้นตอนนี้

## ตัวติดตั้งมองไม่เห็นพื้นที่ว่าง

นี่คือจุดที่ติดนานที่สุดของงานนี้

อาการ: ใน Windows Disk Management เห็นพื้นที่ที่ shrink ไว้ชัดเจน แต่พอบูตเข้าตัวติดตั้ง
Ubuntu Server ไปถึงหน้าจัดการพื้นที่ ตัวติดตั้ง **เห็นดิสก์ แต่ไม่เห็นพื้นที่ว่างก้อนนั้น**
เลยเลือกลงไม่ได้

ลองถาม AI ตัวหนึ่ง ได้คำแนะนำให้ปิด Device Encryption / BitLocker ใน Settings ของ Windows
ทำแล้ว — **ยังไม่ผ่าน**

เปลี่ยนไปถาม AI อีกตัว ได้เพิ่มมาอีกสองข้อ:

1. หลัง shrink แล้วอย่าปล่อยพื้นที่นั้นเป็น unallocated ให้สร้างเป็นไดรฟ์จริงใน Windows
   ก่อน (Drive D:)
2. เก็บ BitLocker recovery key ไว้ก่อนทำอะไรต่อ

พอสร้างเป็น Drive D: ตัวติดตั้งเห็นไดรฟ์นั้นแล้ว — แต่ไดรฟ์นั้นติด BitLocker อยู่ ยังใช้ไม่ได้
ต้องถอดการเข้ารหัสของไดรฟ์นั้นออกก่อน หลังจากนั้นถึงเลือกได้และลงต่อจนจบ

สรุปเงื่อนไขที่ทำให้ผ่าน — ต้องครบทั้งสองอย่าง ทำอย่างเดียวไม่พอ:

| เงื่อนไข | ผล |
|---|---|
| พื้นที่เป็น unallocated เปล่า ๆ | ตัวติดตั้งไม่เห็น |
| สร้างเป็นไดรฟ์แล้ว แต่ยังติด BitLocker | ตัวติดตั้งเห็น แต่ใช้ไม่ได้ |
| สร้างเป็นไดรฟ์ + ไม่มี BitLocker | เลือกได้ ลงได้ |

> ⚠️ **ขอบเขตของสิ่งที่ยืนยันได้** สิ่งที่ยืนยันได้จากเครื่องนี้คือ **ไดรฟ์ที่จะยกให้ Ubuntu
> ต้องไม่มี BitLocker** และการปิด Device Encryption ใน Settings ทำให้เงื่อนไขนั้นเป็นจริง
> ผมไม่ได้ตรวจสอบว่าไดรฟ์ C: ถูกปิดการเข้ารหัสไปด้วยหรือไม่ ดังนั้นอย่าอ่านโพสต์นี้ว่า
> "ปิด BitLocker ทั้งเครื่องแล้วจะผ่าน" — สิ่งที่ยืนยันว่าจำเป็นคือ partition ปลายทาง
> ต้องไม่ถูกเข้ารหัส ส่วนสถานะของ C: เป็นตัวแปรที่ยังไม่รู้
{: .warn}

## ขั้นตอนในตัวติดตั้ง

พอถึงหน้าจัดการพื้นที่:

1. เลือกไดรฟ์ที่เตรียมไว้ (Drive D: ที่สร้างจากพื้นที่ที่ shrink มา)
2. สั่ง edit แล้วเปลี่ยน format เป็น **ext4** และกำหนด mount point เป็น `/`
3. ส่วน **EFI ให้เลือกตัวที่ Windows ใช้อยู่แล้ว ไม่ต้องสร้างใหม่** — ในเครื่องนี้คือ
   partition ขนาด 100 MB

> ⚠️ **ห้ามสร้าง EFI partition ใหม่** ดิสก์แบบ UEFI ใช้ ESP ร่วมกันทั้งเครื่อง ระบบปฏิบัติการ
> แต่ละตัวไปวางไฟล์บูตของตัวเองไว้ในนั้น ถ้าสร้าง ESP ใหม่แล้วให้ Ubuntu ใช้ตัวใหม่
> firmware อาจหาไฟล์บูตของ Windows ไม่เจอ ผลคือบูตเข้า Windows ไม่ได้อีก
{: .warn}

อีกจุดที่ควรติ๊กในหน้าเลือกซอฟต์แวร์คือ **OpenSSH Server** ติดตั้งไว้เลยตั้งแต่ตอนนี้
จะได้ remote เข้ามาทำงานต่อจากเครื่องอื่นได้ ไม่ต้องนั่งหน้าเครื่องต่อจอต่อคีย์บอร์ด
ซึ่งสำหรับเครื่องที่ตั้งใจจะใช้เป็น server มันคือวิธีใช้งานปกติอยู่แล้ว

## ตั้งค่า BIOS หลังลงเสร็จ

รีบูตครั้งแรกแล้วเจอเมนู GRUB มีทั้ง Ubuntu และ Windows Boot Manager เข้าได้ทั้งคู่

จากนั้นเข้า BIOS ตั้งอีกสองอย่าง:

1. **Boot priority** ให้ `ubuntu` เป็นอันดับ 1 เพราะเครื่องนี้จะใช้เป็น server เป็นหลัก
   ถ้าไม่ตั้ง เวลาไฟดับแล้วเครื่องเปิดเอง มันจะไปรอที่ Windows แทน
2. **AC Power Loss = Power On** ให้เครื่องเปิดเองอัตโนมัติเมื่อไฟกลับมา ข้อนี้จำเป็นสำหรับ
   เครื่องที่มีคนอื่นเข้ามาใช้ผ่าน network เพราะถ้าไฟดับตอนไม่มีคนอยู่ แล้วเครื่องไม่เปิดเอง
   ก็เข้าไม่ได้จนกว่าจะมีคนไปกดปุ่ม

### ไม่ต้องปิด Secure Boot

คู่มือลง Linux จำนวนมากบอกให้ปิด Secure Boot ก่อน เครื่องนี้ไม่ได้ปิด และลงผ่านปกติ
ยืนยันหลังลงเสร็จ:

```bash
mokutil --sb-state
```

```
SecureBoot enabled
```

Ubuntu มีไฟล์บูตที่เซ็นลายเซ็นมาให้แล้ว จึงบูตผ่าน Secure Boot ได้ตรง ๆ

ข้อดีของการไม่ไปยุ่งกับมันมีมากกว่าแค่ประหยัดขั้นตอน — การแก้ค่านี้ใน BIOS เข้าข่าย
"สภาพแวดล้อมตอนบูตเปลี่ยน" ซึ่งเป็นเงื่อนไขที่ทำให้ BitLocker ขอ recovery key พอดี
ไม่แตะก็ไม่ต้องเสี่ยง

## สิ่งที่ได้เรียนรู้

| จุดที่พลาดได้ | ผลที่เกิด | ทางแก้ |
|---|---|---|
| ปล่อยพื้นที่ไว้เป็น unallocated | ตัวติดตั้ง Ubuntu Server มองไม่เห็น | สร้างเป็นไดรฟ์จริงใน Windows ก่อน (Drive D:) |
| ไดรฟ์ปลายทางยังติด BitLocker | ตัวติดตั้งเห็นไดรฟ์แต่ใช้ไม่ได้ | ปิด Device Encryption แล้วรอถอดรหัสให้เสร็จ |
| ไม่ปิด Fast Startup | Windows ไม่ได้ shutdown จริง partition ถูกล็อก เสี่ยง filesystem พัง | ปิดก่อนทำทุกอย่าง |
| สร้าง EFI partition ใหม่ให้ Ubuntu | เสี่ยงบูต Windows ไม่ขึ้น | ใช้ ESP ตัวเดิมที่ Windows ใช้อยู่ |
| ไม่เก็บ recovery key | ถ้า BitLocker ขอ key ขึ้นมา = ข้อมูลใน Windows หายถาวร | `manage-bde -protectors -get C:` แล้วเก็บเลข 48 หลักไว้นอกเครื่อง |
| ไม่ติดตั้ง OpenSSH ตอนลง | ต้องต่อจอต่อคีย์บอร์ดเพื่อทำงานต่อ | ติ๊กเลือกตั้งแต่หน้าติดตั้ง |
| ไม่ตั้ง boot priority / AC Power Loss | ไฟดับแล้วเครื่องไม่กลับมา หรือกลับมาบูตผิดระบบ | ตั้งใน BIOS ให้จบตั้งแต่แรก |

บทเรียนหลักของงานนี้: อาการ "ตัวติดตั้งมองไม่เห็นพื้นที่" มีสาเหตุซ้อนกันสองชั้น
และการแก้ทีละอย่างแล้วลองใหม่ทำให้เข้าใจผิดว่าวิธีแรกไม่ได้ผล ทั้งที่จริงมันจำเป็นแต่ยังไม่พอ
เวลาเจอปัญหาที่แก้ข้อเดียวแล้วยังไม่หาย อย่าเพิ่งทิ้งสิ่งที่ทำไปแล้ว
